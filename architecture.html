Intent Classifier

A domain-aware engine that maps free-form language to configured business intents using hybrid retrieval, and declines to answer when nothing fits.

The premise is that intent classification is a retrieval problem, not a generation problem. Each intent owns a set of example utterances. A query is matched against that corpus by two independent retrievers, their rankings are fused, and the winning intent is scored. Every stage is inspectable, and adding an intent means adding examples rather than training a model.

Why fuse by rank

Cosine similarity and BM25 scores live on incomparable scales: one is bounded near [0, 1], the other is unbounded and grows with corpus statistics. Averaging them is not meaningful. Reciprocal Rank Fusion discards the magnitudes and keeps the ordering, so an example that both retrievers place near the top outranks one that either places first alone.

Why sum the best three examples per intent

StrategyFailure mode
take the single best exampleone near-duplicate decides everything; the runner-up margin becomes noise
sum every retrieved exampleintents with more examples accumulate low-rank crumbs and win on size
sum the best threerewards agreement among strong examples, caps the advantage of a large intent

It also gives the score a known ceiling — an intent whose examples take ranks 1 to 3 in both lists — which is what makes the fusion score normalizable into a bounded signal.

Confidence

The fused score is a ranking quantity, not a probability. Returning it as confidence would be misleading, so confidence is computed separately from four bounded signals.

SignalWeightWhat it measures
s_dense0.35cosine similarity of the closest example, rescaled between a floor and ceiling
s_rrf0.25the aggregated fusion score against its theoretical maximum
s_margin0.25how far the winner leads the runner-up
s_support0.15how many retrieved examples back the winner
BM25's raw score is excluded on purpose. It depends on corpus size and document length, so a score of 5.9 means different things in different domains. Its evidence already reaches the decision through the fusion ranking.

The UNKNOWN rule

A result is UNKNOWN when confidence falls below the threshold, or when the closest example is below a hard similarity floor regardless of how well the lexical retriever scored. The response names which rule fired: low_confidence, low_similarity or no_examples.

This matters most for agentic callers. A confident wrong classification invokes the wrong tool, which is worse than admitting the request is out of scope.

Domains

A domain is an isolated intent namespace, and retrieval never crosses the boundary. The same phrase can mean different things in different domains, and a catalogue with hundreds of intents does not dilute a small one.

contract                     employee
├── CONTRACT_SEARCH          ├── EMPLOYEE_SEARCH
├── CONTRACT_SUMMARY         ├── EMPLOYEE_DETAILS
├── CONTRACT_EXPIRY          └── EMPLOYEE_LEAVE
└── CONTRACT_COMPARE

"How many leave days do I have left?" is a valid request in one namespace and correctly UNKNOWN in the other.

Data model

Chroma has no uniqueness constraints, no foreign keys and no cascades, and an insert with an existing id is silently skipped rather than rejected. Every one of those guarantees is therefore enforced in the service layer under a single lock. Repositories sit behind protocols, so configuration can move to a relational store later without touching the engine.

Keeping the indexes honest

Two indexes must agree: the vectors in Chroma and the BM25 corpus in memory. They are updated in the same operation. Adding an example embeds it, writes it, and rebuilds that domain's BM25 index before the request returns, so the new phrasing is classifiable immediately.

Rebuilding eagerly is affordable because the corpora are small — hundreds of short utterances — and it keeps the reported state truthful. GET /domains/{id}/index/status reports the state, a version number that increments on every rebuild, and both document counts; if they disagree, something is wrong.

One tokenizer, used twice. The same function normalizes text when the index is built and when a query arrives. A mismatch between the two is the classic cause of a BM25 retriever that silently finds nothing.

POST /api/v1/classify/debug returns the same decision with the full trace attached: the normalized query and its tokens, every dense hit with its similarity, every BM25 hit with its score, the fused intent ranking, and the four confidence signals. The playground renders exactly that, which makes a surprising classification a five-second investigation rather than a guess.

After the intent: entities and tools

A classification on its own cannot call anything. Once an intent resolves, the engine extracts the values that intent declares and reports the call it maps to.

Everything the model returns is untrusted input

A language model will happily return a key that was never asked for, a date in whatever format it feels like, and an enum value that does not exist. Each value is coerced to the type the intent declared, enums are normalized to the declared spelling, dates become ISO 8601, and any undeclared key is discarded. A required entity that was not found leaves the tool call marked not ready, with the missing names listed, rather than calling a tool with a hole in its arguments.

Extraction never runs for UNKNOWN. Pulling arguments out of a request the system did not understand produces confident nonsense. It is also never on the critical path: a provider timeout leaves the classification intact, with empty entities and a status explaining why.

Each domain speaks its own language

The extraction prompt is layered: base rules shared by every domain, then the domain's system_instructions, then the intent's extraction_hints, all in the system turn; the domain's user_instructions and the conversation history precede the request in the user turn. A contract domain can state that a counterparty is never our own company; an employee domain can state that "me" is the person asking. Neither needs a code change.

An offline provider for the whole flow

LLM_PROVIDER=mock substitutes a rule-based extractor that reads exactly the prompt a model would receive. It is not clever, and that is deliberate: its job is to make instructions, history, validation, carry-over and tool routing all execute for real without a key, with output stable enough to test against.

Conversations, not queries

Running it in production

ConcernDecision
Authentication API keys rather than OAuth. This is a service-to-service component, and an internal platform with no identity provider is better served by a credential the caller can rotate than by a login flow nobody operates.
Health probes are unauthenticated A probe that needs a secret is a probe that breaks when the secret rotates.
Metrics labelled by route template A label containing a domain id creates a new time series per domain. That is how a metrics backend falls over.
Audit log as append-only JSONL The workload is append-heavy and read rarely, and a file survives the database being rebuilt, which matters when the database is also the configuration store.
Query text not recorded by default User queries carry personal data. Recording them is a decision an operator makes deliberately.
Tracing off by default A collector is infrastructure, not a library. With no endpoint configured the exporter would retry in the background and add latency to every request.
Indexes warmed at startup Otherwise the first request after a restart pays the build cost, and index health reports a problem for a service that is perfectly healthy.

Changing retrieval safely

Retrieval is the highest-risk thing to change here, because a regression is invisible until someone notices the wrong tool being called. Variants are therefore named and explicit, and a request is assigned one by hashing its request id, so the same id always lands on the same pipeline and a reported result can be reproduced.

StrategyTop-1UNKNOWN detectionp50
hybrid_rrf (default)90.6%90%3.4 ms
dense_only87.5%70%3.4 ms
bm25_only65.6%40%0.6 ms
hybrid_wide87.5%100%3.7 ms

This is the argument for hybrid retrieval restated as a measurement rather than an opinion. Either retriever alone is worse, and lexical-only is dramatically worse at knowing when to decline. A single-retriever variant is scored against its own ceiling, so it is not penalised for evidence it was never configured to collect.

The same evaluation runs from the UI against the live catalogue, so a threshold change or a new batch of examples can be judged immediately instead of on trust.

Deliberate boundaries

DecisionReason
Classification is separate from tool execution A result reports the mapped tool; the caller decides whether to run it. The caller owns the credentials, the retry policy and the blast radius. A side-effect-free classifier can be shared by an API, a UI and an agent at once.
Retrieval is synchronous, extraction is not Retrieval is CPU-bound and runs in a worker thread; extraction is a network call and runs on the event loop. Mixing them in one handler is the mistake this separation avoids.
The LLM is not in the classification path Retrieval is deterministic, inspectable and evaluable. The LLM is reserved for entity extraction, where generation is actually the right tool.
The BM25 index is never persisted as truth Rebuilding from Chroma is fast, and a second on-disk copy drifts the moment the tokenizer changes.
One process, one worker Embedded Chroma is a single-writer store. Concurrent writers risk corrupting it.

Evaluation

A held-out set of 42 queries — none of them training examples, 10 of them deliberately out of scope — is scored on every run. Accuracy is a regression test, not a launch metric.

MetricResult
Top-1 accuracy90.6%
Top-3 accuracy100%
UNKNOWN detection90%
Valid queries wrongly refused3.1%

Top-3 at 100% with top-1 at 90.6% says something specific: retrieval is finding the right intent every time, and the remaining errors are ranking decisions between close neighbours. That points at the aggregation and confidence stages, not at the retrievers.

The thresholds were chosen by sweeping them against this set rather than by taste. The sweep prints the trade-off directly: a stricter similarity floor reaches perfect UNKNOWN detection but starts refusing valid queries. Which side to err on depends on whether a wrong tool call costs more than a refusal.

What comes next

  • Feedback capture. Recording whether a classification was acted on turns the audit log into training signal and lets thresholds be recalibrated on real traffic rather than on a fixed evaluation set.
  • A reranker. The remaining errors are ranking decisions between close neighbours, which is exactly what a cross-encoder is good at. Top-3 already sits at 100%, so the headroom is real.
  • PostgreSQL for configuration. Not needed yet. It becomes justified when multi-tenant authorization or heavy audit querying arrives; the repository protocols exist so that swap stays contained.
